# Play statistics: done and to do

How the game counts what players do, sent to PostHog, and what is still to add so the numbers explain how the game is played. Crash reports and logs are separate and go to Sentry (`src/app/sentry.ts`).

Tick an item off when it is done, with the commit or release it landed in.

## How it works

- **Where they go.** PostHog's US cloud, the free tier, project "Default project" (id 672370). The project key is in `src/app/analytics.ts`. Like Sentry's DSN, it only says where to send, so it is safe to publish.
- **Which copies send.** Only the published web game (`production`) and the installed desktop app (`desktop`), as decided by `src/app/environment.ts`, which Sentry uses too. The dev server, `yarn preview`, the desktop app run from this folder and every test send nothing.
- **Tests and bots never send.** A browser driven by a program sets `navigator.webdriver`, and crawlers and headless browsers name themselves in their user agent; either keeps even a published copy from starting PostHog (`src/app/automation.ts`). That covers every Playwright test, in a browser or the desktop app, including a packaged app tested with `PP_APP`. Checked on 18 October 2026 with a build allowed to send: under Playwright PostHog never started, and in an ordinary browser it did. The balance bot (`yarn balance`) and the unit tests run the simulation in Node and never load the analytics at all.
- **Sharing is on until switched off.** Settings → Privacy → Share play statistics. Switching it off stores `off` under `pressure-point-analytics` (`src/storage/analytics.ts`) and stops PostHog capturing; switching it back on forgets the choice.
- **Only the events the game sends.** The SDK is the `posthog-js/dist/module.no-external` build, with autocapture, page views, session recording, surveys, feature flags, heatmaps and exception capture all off, and nothing loaded from elsewhere. Players are a random id kept in local storage, with no person profiles (`person_profiles: 'never'`). The save's name, which is the player's own, is never sent.
- **IP addresses are not stored.** Since 18 October 2026 the project discards them ("Discard client IP data" under PostHog's Project settings, `anonymize_ips`). PostHog still looks up the country from the address before dropping it, so events keep their `$geoip_country_code`. Players are told apart by PostHog's random anonymous id, kept in the game's local storage, never by IP address. Events from before the change, only test data, still have one.
- **The page allows it.** `index.html`'s content security policy lets the game connect to `https://us.i.posthog.com` and `https://us-assets.i.posthog.com`.
- **Two kinds of event.** Most are found by comparing the game, once a second, with how it stood a second before (`src/app/play-events.ts`, run by `watchGame` in `src/app/analytics.ts`), so the game core knows nothing of them. Choices made only in the interface (offers, menus, overlays, settings) are counted where the player clicks.
- **What the watcher adds.** Once a second, while the game runs with its doors open, `watchGame` also notes the stage holding guests up (`Sim.bottleneck()`), the advisor's nudge (with people's names taken out) and how the staff are, and sums them up in that month's `month_ended`. It times every frame drawn while the page is seen (`FrameStats` in `src/app/frames.ts`), leaving out the first 3 seconds of a game, which go on setting the scene up, and any gap of 2 seconds or more, which is the page put away rather than a frame.
- **Performance metrics.** Each frame's time also goes to PostHog's Metrics (open alpha, 30 days' retention) as the histogram `frame.duration` in milliseconds, from the service `pressure-point`, with `app_version` and `platform` attributes. The SDK adds every frame to one histogram and sends it once a minute, and at the last moment as the page closes. It respects the sharing switch like the events do. The histogram's buckets are PostHog's defaults (up to 10, 25, 50, 100 and 250 ms and on), which are enough to tell smooth from 30 frames a second from stutter. Turn the viewer on once under Metrics → Enable metrics; the data is stored before then. This is for trends by version and platform; the summaries are for which players struggle and why.
- **Refusals.** The build tools count every action they turn down, with the reason shown under the cursor (`Tools.refuse` in `src/app/tools/tools.ts`), and a locked button counts a press, with its words and tooltip (amounts left out). Each action and reason is counted at most once a minute, so trying the same spot over and over counts once.
- **Tests.** `tests/unit/play-events.test.ts` covers every event found by comparison, how a month feels, the sharing switch, telling tests and bots from players, and the frame times.

## What is counted

Every event also carries `app_version`, `platform` (`web`, `darwin` or `win32`), `environment` (`production` for the web game, `desktop` for the app, `preview` for a local build allowed to send while checking the statistics) and `play_id`, a random id for the page it came from. Leaving a game reloads the page, so a `play_id` is one session of one game. Events from a game also carry `center`, `day`, `stars` and `cheated`. Cheated games are left out of every chart by the project's test account filter.

## In PostHog

- **The dashboard:** [How players play](https://us.posthog.com/project/672370/dashboard/2226587), pinned. It has the new-player funnel, players who come back, players per day, how long sessions last, time at each speed, how games go month by month, why guests leave unhealed, staff who quit, games that went into the red, offers taken up, turned down and let lapse, menus opened, items used, where the money comes from and goes, what holds centers up, staff mood and guest patience, what the game turns down, how emergencies, outbreaks and visits end, and frame rate by graphics chip.
- **Test account filters** leave out events with `cheated` true, from a `preview` build or from a `localhost` page, as well as PostHog's own internal users, and new insights use them by default. The SQL tiles can't use them, so each repeats the same three conditions itself; a new SQL tile needs them too:

  ```sql
  coalesce(toString(properties.cheated), 'false') != 'true'
  AND coalesce(toString(properties.environment), '') != 'preview'
  AND coalesce(toString(properties.$host), '') NOT ILIKE '%localhost%'
  ```

### Reliability

- [x] **`game_left` can be lost.** It goes out as a beacon while the page closes, and quitting the desktop app or a phone closing a hidden tab can drop it. Now a `play_summary` with the whole session so far goes out every 5 minutes of play and whenever the page is hidden, so at most a few minutes are ever lost.
- [ ] **Ad blockers stop many web players' events.** PostHog's domain is on the common block lists. GitHub Pages cannot proxy requests, so this needs a small proxy elsewhere, such as a Cloudflare Worker on a domain of the game's own, with `api_host` and the content security policy pointed at it.
- [ ] **Players who switch sharing off are not counted at all**, by design. Counting how many switch it off would need a count with no player id, which PostHog does not offer; leave it.
