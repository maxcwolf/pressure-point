# Architecture

Pressure Point Institute is a browser game that also ships as a desktop app. The same code runs in both: the desktop app is an Electron window around the web build.

## The layers

| Folder               | What it is                                                             | May import from                                                                                                            |
| -------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `src/core/`          | The game itself: rules, state and content. No browser, no drawing.     | Nothing outside itself                                                                                                     |
| `src/storage/`       | Saved games and preferences, kept in the browser's storage.            | `core`                                                                                                                     |
| `src/render/`        | The 3D picture of the game, in Three.js.                               | `core`, and the icons' atlas in `ui/icons/generated/`                                                                      |
| `src/audio/`         | Sound effects, music and the announcer's recordings (`src/sounds/`).   | `core`, `storage`                                                                                                          |
| `src/ui/`            | The interface over the picture, in Preact.                             | `core`, `storage`, `audio`, types from `app` and `render`, and a few `app` helpers (play statistics, feedback, tool hints) |
| `src/app/`           | Startup, input, the build tools and the frame loop. Wires the rest up. | Everything above                                                                                                           |
| `electron/`          | The desktop app's main process and preload script.                     | Nothing in `src/`                                                                                                          |
| `src/lab/`           | The model lab and the icon sheet, pages for the dev server only.       | Anything; nothing in the game imports it                                                                                   |
| `src/styled-system/` | What Panda makes from `panda.config.ts`. Not committed, not edited.    | Itself                                                                                                                     |

Dependencies point toward `core`. A lint rule and a separate TypeScript project (with no browser types) stop `core` importing anything outside itself, so the whole game can run in a unit test with no page and no renderer. Lint rules hold `storage`, `render` and `audio` to the imports in the table too, and keep the browser's globals (`window`, `document`, `navigator`, `localStorage`, `sessionStorage`) out of `core`. Anywhere in `src/`, the center's money changes only through `earn`, `spend` and `recoup` in `core/sim/economy.ts`, so the bank always agrees with the books: a lint rule turns down any other change to `money`, but where a new game, an upgraded save or a sandbox game is set up with what it holds. Every preference kept between games, the sound and music switches among them, goes through `storage/`.

`startGame` in `app/game.ts` is where a game is put together, each part after the parts it needs: the simulation, the view, the build tools, the saving, the interface, input, then the loop. Nothing built earlier reaches for a later part. The tools and the saves report back to whoever called them rather than to the interface: a plot of land clicked to buy comes back from `Tools.pointerUp` for the pointer to ask about, and a save that fails comes back as a warning for its caller to show. What the floor shows for the interface, the overlay chosen or the plots in the Land tab, comes from `HudState.floor`.

## One frame

`src/app/loop.ts` runs this once per frame:

1. Move the camera for any keys held down, or the mouse at the edge of the window if edge scrolling is on.
2. Unless a dialog is open, which has the clock to itself, the clock is stopped as a room or an item is taken up to place, unless the player has turned Pause while placing off (`pauseToPlace` in `storage/controls.ts`), and started again at its old speed once it is down (`sim.watchPlacing`, `core/sim/placing.ts`): the speed to go back to is kept on the `SimContext`, not saved, so the tutorial can tell a pause the game made from the player's. Then `sim.tick(dt)` advances the game.
3. The floor overlay is redrawn if it is due, or the item in hand has a new preview, or another overlay has been chosen (which fades in), and `view.render(dt)` draws it all.
4. `sim.drain()` hands over what happened (sounds, toasts, floating text) and the interface shows it.
5. The interface redraws if something changed, or five times a second regardless.
6. Autosave, every five minutes unless the player has chosen otherwise (`storage/controls.ts`). The game is also saved as it is left or hidden, whatever the choice.

Input goes the other way. Pointer and keyboard handlers in `src/app/` call the build tools or the simulation, and the next frame shows the result. The build tools (`app/tools/tools.ts`) hold one `Tool` at a time. The sketch tool is the room tool's first two steps, its drag and its door, ending in a sketch rather than a blueprint; either can be handed floor to start from (`held`), which a click keeps as it is and a drag replaces, as Build here and Move do for a sketch. A refusal whose `Check` names a sketch selects it. In an open blueprint, a piece of its furniture clicked with nothing in hand is picked up to move (the `move` kind of `PlanSub`), kept in its room and moved for nothing, as a built item is.

## The simulation (`src/core/`)

- **State is plain data.** `GameState` (`core/state/types.ts`) is JSON all the way down, so saving is `JSON.stringify`. Anything that can be rebuilt from it, such as the tile grid, is kept out of it.
- **Content is data too.** Rooms, items, roles, treatments and conditions are tables in `core/data/`. Adding one means adding an entry, not writing new logic.
- **Logic is functions.** Each file in `core/sim/` covers one area (guests, staffing, stations, building, economy and so on) as functions that take a `SimContext`: the state, the `World` grid built from it, the queue of events and the ambience grid. Functions that need none of that take no context and are pure.
- **The sim's modules import each other one way.** Of the pairs of files that imported each other, only outbreaks and runaways are left, and a unit test (`tests/unit/sim-imports.test.ts`) fails on a new one. At the bottom are questions that change nothing, which any module may ask: what the center has (`inventory.ts`), where people stand and how they walk (`movement.ts`), and what an item does, read from its fields in `core/data/items.ts` (`tending`, `bin`, `hamper`, `extinguisher`, `heatPerUse`) rather than from its type. Above them are the staff and guests at work: `posts.ts` (taking up a post and leaving it), `lines.ts` (choosing a station and waiting in its line), `staffing.ts`, `guests.ts` (guests once they are in), `arrivals.ts` (who comes, and when), `shop.ts`, `stations.ts`, and `repath.ts` for finding everyone a new way when the building changes. Some of them loop with the features that both call into the day and are called from it (house calls, courses, classes, bad trips, the rival and the twists): 14 modules reach each other in a loop, and the test keeps it from growing. On top sits the month: `economy.ts` keeps the books, `payday.ts` closes the month, `news.ts` logs the quarter's news and `paper.ts` prints it. A new question goes low down; new code that changes the center imports what is below it, never the other way.
- **`Sim` is the front door.** The rest of the game talks only to the `Sim` class, which runs the clock and passes each call to the function that does the work.
- **The game reports, it does not draw.** It queues events (`core/sim/events.ts`); the interface decides how to show them.
- **Every game is set in a center** (`core/data/centers.ts`): the sandbox, or one of the campaign's. A center decides where the building stands on the lot (its `Plot`), the starting money, and the objectives for each star. The `World` works out the building's footprint (`core/footprint.ts`) from the center's plot and the land bought next to it: the rectangles it is built from, its front door, and a mask of the tiles inside. Each center lists the plots of land it sells (`PlotDef`), and `core/land.ts` says which are for sale and for how much. A plot either joins the building or stands apart with its own entrance and a path of paving outdoors; the `World` numbers the buildings, and walking between them is ordinary pathfinding through each entrance's door. Nothing else assumes a fixed building or a rectangle. The outer walls, their windows and the rooms against them are worked out from the footprint's edges (`render/outer-walls.ts`, `render/room-walls.ts`), and the scenery is built again when it grows. Objectives are small specs (`GoalSpec`) that `core/sim/goals.ts` checks against the game.
- **The campaign is kept apart from saved games** (`storage/campaign.ts`): the best stars in each center, the gifts made to the Foundation in each, the achievements earned, the items, floors and walls unlocked with karma, and the lessons shown (`CampaignProgress`). Its rules are pure functions in `core/campaign.ts`. A game only carries its own `achieved` list, topped up from the campaign when it starts, so an achievement is never awarded twice. Karma is worked out from the stars, the gifts and the achievements, with any the cheat console added (`bonus`) on top, never stored as a total. The Foundation (`core/sim/foundation.ts`) takes a center's three gifts once every star there is earned.
- **The day count is time since opening; the calendar runs ahead of it.** `s.day` counts days since the center opened, and paydays, monthly reports, the year's awards and the days of the first emergency, visit and mishap count from it. A game keeps the month it opened in (`startMonth`, 0 for January, which old saves get), and the season, the weather, snow, the light and the date shown read the calendar day instead (`calendarDay` in `core/format.ts`), the count moved on by that many months. `OPENING_MONTH` in `core/state/game.ts` opens Willow Lane in March. `dateOf(day, startMonth)` gives the calendar's month and the year of running the center, so the year shown turns with the awards.
- **A room pencilled in is not a room.** `GameState.sketches` holds sketches (`core/sim/sketches.ts`): a kind of room, a rectangle and a door, drawn and erased for nothing. Nothing that reads `s.rooms` sees them, and the grids, pathing and everything the sim works out leave them out; the build rules alone read them (`sketchAt`, `sketchOverlap` in `build-rules.ts`), turning down an item, a room, a resize, a template or another sketch over one with a `Check` that names it. Building one swaps it for a blueprint (`buildSketch`), and a blueprint can be swapped back (`sketchBlueprint`). Whether one still fits is worked out by `sketchFit` in `build-rules.ts` (it fits, waits for its land, has its doorway blocked, or no longer fits) and kept by the world for each sketch until `version` or the grids change (`World.sketchFit`), so the floor, the labels, the Rooms menu and the inspector share one answer; it is never saved. A sketch pencilled in from a template keeps a copy of its `Layout` and the template's name (`Sketch.layout`, `Sketch.template`), since templates are kept in the browser, not the save; its fit is then `layoutValid` sparing itself, and Build here builds it whole through `buildLayout`. The Plans overlay is an `OverlayMode` that colors nothing (`colorsFloor`): it veils the floor canvas under the sketches (`View.setPlans`) and swaps the overlay key for the list in `PlansKey`, at the head of the right-hand column.
- **Fires and accidents are things in the center, warned of first.** A fire (`core/sim/blazes.ts`, its numbers in `core/data/blazes.ts`) is a `Blaze` in `GameState.blazes`: only a machine smoking with wear catches fire, when it overloads, and it spreads to whatever wears out beside it in its room until a Caretaker, the room's sprinklers or the fire brigade puts it out. Which rooms are covered, by sprinklers or a working Fire Extinguisher near the door, is one rule in `core/sim/fire-cover.ts`, which the inspector, the Caretaker and the Fire safety overlay share, and which judges a blueprint as it will stand once built. An accident (`core/sim/accidents.ts`) is a piece of litter with an `accident` kind, a poop or a puddle, left by a waiting guest bursting with no Restroom to use; a Caretaker cleans it up ahead of other litter. The sandbox can switch both off (`blazesOn`, `accidentsOn`).
- **Why a treatment failed is read off the roll.** `core/sim/failures.ts` takes the reasons from the very terms `successChance` in `stations.ts` used, rather than working them out again afterwards, and keeps the latest failures (`GameState.failures`) for the casebook.
- **The town paper only tells what happened.** `core/sim/news.ts` logs the quarter's news as it is told (`GameState.news`), each item with the facts its story is filled from, and on the payday that closes the quarter prints the biggest as the headline, from the bank of headlines and each center's masthead and column in `core/data/headlines.ts`. The issue is kept word for word (`GameState.paper`). None of it changes the simulation.
- **Staff come with quirks.** The roles and the quirks a member of staff can have are in `core/data/staff.ts`; an applicant is made in `core/people.ts`, with one to three quirks that do not clash and now and then a rare one, and `ui/lib/quirks.ts` writes them out. Staff challenges (`core/sim/challenges.ts`) never ask what one of the next star's objectives already asks.
- **Some features are still being tried out.** `FEATURES` in `core/data/features.ts` lists them, each on or off in a game (`GameState.features`, read with `featureOn`), switched under Feature testing in Settings, and new games start from the profile's choices (`pressure-point-features` in `storage/settings.ts`). Code for one asks `featureOn` first, so with it off a game plays as if it were not there. The only one today is the ailments going around town (`core/sim/waves.ts`): a week's warning, then a month of guests on top of the usual, the treatment opened early if it was still waiting on a star, and any guest the center cannot treat yet turned back at the door.
- **The tutorial and the lessons are part of the game.** `core/sim/tutorial.ts` walks a new Willow Lane game through its opening a step at a time, then through the first game's heads-ups (`core/sim/primer.ts`) as steps of their own. `core/sim/lessons.ts` opens a card the first time something worth explaining happens; the campaign keeps the lessons shown, so each comes once across the campaign. Whether a game has either is the profile's choice (`pressure-point-tutorial`).
- **Random numbers are seeded.** Everything random goes through `core/random.ts`, so a test can replay a game exactly.

## Rendering (`src/render/`)

`View` owns the Three.js renderer and composes one object per layer: floor, rooms, items, people, litter (soot and accidents among it), bad vibes, snow, rain, the rival's storefront, the fire brigade's truck (`brigade.ts`), the land around the building, the heatmap and halos of the overlays, what is selected, camera and picking. Each layer keeps its own meshes in step with the game state. A machine's gag (`render/gags/`) is a script for each machine in `gags/scripts/`, plain data with no Three.js in it, worked out every frame from the game by one `GagClock` that the items and the people layers share, so a machine and the guest inside it keep in step. Models are built in code, one file per item in `models/items/`, from the shared shapes and materials in `models/parts.ts`. There are no art files. Items are held to one guideline so they read as a family beside the people, written at the top of `models/parts.ts`: no structural member thinner than 6 cm (8 cm when taller than a person), corners rounded in proportion to the part (`corner`, `soft`), capsules for what ends in the air, smooth foliage, and strong color only on the part that matters. The floor is one canvas texture at 64 px a tile (`floor.ts`), repainted whenever the world changes, with a few tiles of grain made once and drawn over the plain floors. Rooms pencilled in are painted into it too, after the rooms (`paintSketch`): a wash and hatching in the room's trim, or amber where it no longer fits, a dashed outline and the door in orange, with a remembered room's furniture as darker footprints and its windows in blue, at no cost in draw calls; while the Plans overlay is on, a navy veil is painted over the rest of the floor first; their labels are HTML over the scene, placed each frame from the point under them as floating money is (`SketchLabels`). Every part is a draw call, and a part that casts a shadow is a second one, so only parts big enough to show a shadow cast one: `trimShadows` turns it off for the rest of each item and person as it is built. An item's parts that never move are merged into one mesh for each material as it is built (`models/merge.ts`), and every copy of that item shares the merged shapes; the parts its `ItemParts` name are left alone so they can still move. The cues an item gives of its wear, dirt, noise and warmth (`item-cues.ts`) are a few parts added to its model the first time each is needed, from shared shapes, and hidden while off, so an item in good repair and at rest draws nothing more. A mishap that has stopped an item shows the same way (`STOP_LOOKS`): in a power cut its lights and glows go out and smoke and the like drawn without light dim indoors; in a freeze its parts are glazed with ice and icicles hang off it; and wasps swarm over it as one cloud of dots. A stop swaps each part's material for its stopped look (`dressStopped`), made once from that material and shared like it, so a stop adds no materials for each item, and puts them back after. A finished room's walls, the building's shell and its back-wall windows are merged the same way, into shapes of their own that are freed with them (`owned` in `disposal.ts`). People are drawn in batches (`crowd.ts`): the same part of everyone, such as every head or every left shoe, is drawn in one go, each in its own color, so a crowd costs hardly more than a few people. Each person keeps their own meshes, posed as usual, and the batches copy where they are just before each frame is drawn. Someone seen from afar, under about 100 pixels to the meter, is drawn with stand-ins for their finely built parts that have about half the sides, and under 60, as at the distance the game is mostly played at, with stand-ins of a quarter, both made alongside each shape in `models/character-detail.ts`: from there, the full shapes' sides would be finer than a pixel and cost as much to draw. How someone feels shows on their face by giving their mouth and brows another pair of shared shapes (`showExpression`), so each expression is a batch of its own rather than a part per person. Eyes open and shut the same way. A person's build is a scale on their body that spares the head, so every hat, pair of glasses and symptom on a head fits every build, and glasses and shoes are shared shapes like any other part, so the crowd draws them in a batch whatever their color. What makes up a look beyond its height (the build, glasses and shoes) is taken from the spare bits of the number the height is drawn from, so making someone up takes no more of the game's random numbers than it did. `pose.ts` poses everyone every frame from the game state, by turning their joints, and counts their stride from the ground they cover rather than the clock, so their feet plant where they land at every speed of the game: a waiting guest's patience (`PATIENCE_SIGNS`) and a member of staff with nothing to do add to the pose in the same way, and all a person's rig remembers between frames is where they were and which way they faced last frame, how far they have walked, when they last had nothing to do, and where they are being shown, below. Where a person is drawn can differ for a moment from where the sim has them (`motion.ts`): the sim puts a guest on a table, and takes them off it, in one tick, so they are shown walking up to its edge and climbing on in 0.9 seconds of the clock whatever the game's speed, and climbing back off to its edge the same way backwards, in the same time, before walking on after the sim; a guest healed where they were treated is held there while the puff of the cure plays, then catches up; and people standing or walking are drawn stepping up to a quarter of a meter aside from anyone too close. None of it reaches the sim, so nothing it counts changes. The ring under someone selected, the chevron over them and the halos are put where they are drawn (`drawnAt` in `people.ts`). What a person is doing at an item (a receptionist checking someone in, a guest at a vending machine, a Caretaker on a chore) is worked out by the people layer once a frame (`actOf` in `acts.ts`) and handed to `poseChar` with the other cues, which poses it with anything held, a cup or a wrench, built the first time it is needed and hidden otherwise (`models/held.ts`). The speech bubble over a head is chosen there too (`bubbleWanted`), alarms first, in red or amber only for what is wrong at that moment (a guest fed up or getting worse while waiting, bursting or parched in the queue, staff about to quit or worn out with no break coming), and white for everything the sim says; it is shown by `bubbles.ts`: popped in and shrunk away, an alarm pulsing, all of that left out when the system asks for reduced motion (`prefersReducedMotion`), and held at least 1.4 seconds of real time however briefly the game said it, all from what the bubble's sprite remembers. Bubbles and markers are sized by `readable` (`readable.ts`), which grows a sprite just as it is drawn, and back after, so it covers at least so many pixels as the camera pulls back, but never more than 1.5 times its own size (`MAX_GROWTH`); and markers over items go one to a huddle of neighbors (`markers.ts`).

A room (`rooms.ts`) is built from the boxes `room-walls.ts` works out for its walls, windows and door, and is built again only when the room or the camera's turn changes. Trims (`ROOMS` in `core/data/rooms.ts`) are the first cue for which room is which, so every two rooms that can stand in the same center, and the building's teal, stay apart in typical vision and in simulated protanopia, deuteranopia and tritanopia, which `room-trims.test.ts` checks in OKLab. A door has a frame in the room's trim on both faces of its wall, a raised threshold over the one `floor.ts` paints, and in a tall wall a white panelled leaf propped open; in a wall cut low only the stubs of the jambs show. A window (`windows.ts`) in a wall cut low is cut with it, to a strip of its glass along the top of the stub between the ends of its frame, so nothing of it stands in the air in front of the people in the room; things hung on a wall cut low still show as faint ghosts where they hang (`hung.ts`). The room's sign (`models/sign-plaque.ts`) is a plaque in its trim with its icon on both faces, so it reads from either side of the wall and so from every turn: it stands on the head of the door's frame in a tall wall, or on a post beside the doorway in a low one, clear of whoever walks through. Its board is merged with the walls' trim; the icon is one more draw call, and the lamp on top and its halo two more, left out of the merge. `RoomsLayer.update` reads each lamp's state from the sim every frame (`room-lamp.ts`): grey while unfinished, red if a station or a required item is worn out, amber if the room has stations and nobody is at their post at one, green otherwise. The lamps share one emissive material for each state, so lighting and pulsing them (amber and red pulse) changes a few materials, not a mesh for each room.

What is selected shows over everything (`overlays.ts`): the ring is drawn a second time, faint, only where something stands in front of it, a chevron bobs over a selected person above any speech bubble, and a selected room has a gold outline just inside its walls. The pointer looks at what is under it once a frame at most (`app/pointer.ts`), and whatever a click would select glows, fading in: a room's floor under a faint sheet, a person or item under copies of its parts drawn over it, which leaves the crowd's batches alone and costs a few draw calls only while something is hovered. It also notes the finished room under it, with nothing in hand and no button held (`HudState.pointedRoom`), and unless the player has turned Queue on hover off (`queueTip` in `storage/controls.ts`), after a moment `RoomTip.tsx` shows that room's line in the tooltips' bubble: placed over the room each frame as the camera moves, its words worked out (`ui/lib/queue-tip.ts`) only as the floating text is drawn again, a few times a second. The preview of what is in hand (its ghost, tiles and door marker) sits in one group, which shakes across the screen when a click with it is turned down. An item new or moved settles in with a squash (`settle.ts`), which `ItemsLayer.sync` hands the view by returning the models it built for items that landed.

The camera (`camera.ts`) eases toward where it is sent, how far back it is asked to sit and how far round it is turned, each at a rate a second (`camera-math.ts`), so a glide or a quarter turn takes as long at 30 frames a second as at 144. A jump to a spot eases the zoom along with the glide, and the wheel zooms toward the spot under the pointer, moving the target so that spot stays put. The walls are cut low for the quarter the camera is nearest (`CameraRig.facing`), so they swap halfway through a turn, where the walls changing are side on to it, not on its first frame. A player whose system asks for reduced motion gets cuts instead: a jump, a turn and a wheel's zoom happen at once, and no item squashes or preview shakes.

The overlays are drawn two ways. Surroundings, calm, temperature and upkeep are one soft field (`heatmap.ts`): a texture of one pixel a tile, smoothed between them, on a plane just above the floor, with values from `ui/lib/overlays.ts` centered on ordinary so that ordinary is drawn clear and only what stands out shows, and the item in hand is previewed through the same field. Patience, needs and staff energy ring the people instead (`halos.ts`): a band at each person's feet, following them each frame, drawn a second time faintly through whatever stands in front of it. Both read their colors from the `overlay` roles in `ui/theme/panda/semantic.ts`, as the `--colors-overlay-*` variables Panda makes of them, so the floor matches the key in the picker; land for sale keeps hard tiles.

The light is in `lighting.ts`: a hemisphere light for the sky and the light thrown back up off the ground, and one sun that casts shadows. The renderer draws with neutral tone mapping (Khronos PBR Neutral) at a touch over unit exposure, which keeps the cream floors, the teal trim and the pastels the colors they are picked as while letting a bright highlight roll off rather than clip; ACES filmic was tried and grays them. Each setting (`setting.ts`) has its own light: the sky's color, the bounce off its ground (grass green in the park and orchard, warm sand at the seaside, blue-white in the snow, warm gray stone downtown) and the sun's warmth. The sun follows the point the camera looks at, and its one 2048 px shadow map is sized to the camera's zoom (`shadowReach`), so shadows are crisp close in and still cover the view far out; the normal bias follows the texel size. The light tells the time and the season (`daylight.ts`, pure numbers with their own tests): through each game day the sun and the sky ease from a low, warm, faintly rosy morning at opening, through plain noon from about a third of the day to two thirds, to an amber evening at closing, then back round to morning so the day wraps without a jump; the sun dims to no less than four fifths and the sky hardly at all, so the cream floors warm rather than gray, and the sun keeps its direction, since the shadow follows the camera and the walls are cut low toward it. A game day is six seconds, so the day strays only a quarter of the way from noon at normal speed and less at double and triple speed (`dayDepth`), easing between, so the light does not pulse. Each season tints the sky and the sun a little on top of the setting's own light (cooler in winter, warmer in summer, golden in autumn), and shifts the ground: a lawn fresher in spring, warmer in summer, gold in autumn and pale in winter, sand a touch, paving a little paler in summer and darker and wetter in autumn and winter (never green or white), snow not at all. `settingOf` gives a setting's colors in the season, so the lawn (one shared `LAWN` material the light recolors rather than the scenery being built again), the backdrop and the lot's open-ground tiles on the floor change together; the floor is repainted when the season turns. The trees turn with it: their leaves and the orchards' canopies and apples are materials of their own (`leavesFor` in `models/tree.ts`, `orchardFor` in `models/orchard.ts`), which the light repaints with the season, nothing built again. Downtown (The Exchange) the ground is paving: the floor paints slabs two tiles long in rows set half a slab along, `LAWN` carries the same joints past the lot as a repeating texture, and land not yet bought is painted as gravel lots with a curb (a setting's `plots` shades), so it still reads as land for sale on a plaza that is otherwise all one ground. Its streets, office blocks, street trees and lamps (`models/downtown.ts`) are merged by material into a few meshes, and the blocks stand far enough back (`officeBlocks`, with its own tests) that, whichever way the camera is turned, they hide none of the lot. Willow Lane's lot is on a high street (a center's `highStreet`): the road and its pavements run on past the lot, with a pavement along the far side, hedges on a low brick wall broken for the path to the door and for every plot that reaches the street, and lamp posts only beyond the lot's own frontage, which the opening view looks over (`buildHighStreet` in `scenery.ts`, `models/high-street.ts`). `lightScene` puts all of it on the lights each frame. A storm dims the sky and sun together on top of the hour (`lightLevel`), easing in and out, and takes most of the warmth out of the light (`stormGray`), so a stormy evening is gray with a trace of amber. Snow falls over the lot outside the building (`snowfall.ts`), never on the floors of the rooms the game shows with no roof: heavy while a center is snowed in, and a fifth as many flakes, smaller and slower, in a flurry of light snow (`flurrying` in `core/sim/flurries.ts`), which falls for three days once or twice a winter wherever the climate goes below freezing, worked out from the calendar like the snowed-in spells, and changes nothing for the center. A power cut is not dusk: the sun keeps 85% so the lot stays in daylight, the sky dims and cools, and the building's inside falls into shade (`shadeInside`) under a roof that is never drawn but casts a shadow, laid over the building's footprint and set off toward the sun by its height so its shadow lands on the floor and everything inside and nowhere else. A save's picture on the title screen is taken by noon light whatever the hour (`atNoon`), and the scene's screenshot tests hold the clock at noon. Materials come from `mat()` in `models/parts.ts`, one per color, roughness and glow: painted surfaces are satin, wood and lacquer a little glossier, and cloth and skin take a faint sheen, with no metalness, so each kind of surface takes the light its own way without any more materials.

## Icons (`src/ui/icons/`)

The game draws its own icons rather than using emoji, so they look the same on every computer and match the clay style. Each is an SVG on a 32-unit square in `src/ui/icons/`, named by a stable id that starts with its family: `bubble-`, `marker-`, `room-`, `role-`, `discipline-`, `overlay-`, `ui-`, `season-`, `item-`, `technique-`, `course-`, `feeling-`, `award-`, `achievement-`, `mishap-` or `standing-`. `yarn icons` (`scripts/make-icons.mjs`) checks every drawing and builds five things from them, all committed: a sprite sheet the interface draws from (`<Icon id="room-massage" />`, in `ui/components/common/Icon.tsx`), a second sprite sheet for icons at 20 pixels and under, a texture atlas and its map of where each icon sits for the scene (`iconTexture(id, way)` in `render/models/icons.ts`), the box round each drawing's ink (`ink.json`, for the lint below), and the list of ids, `IconId` and `SceneIconId` in `core/data/icon-ids.ts`, so a misspelled id does not compile. An `Icon` measures the size it comes out at in pixels of the screen with a shared `ResizeObserver`, so it goes by pixels however its size was written (`1.3em` beside 17-pixel words is 22 pixels, and big): at 20 and under (`isSmall`) it draws from the small sheet, so an icon of 16 on a screen of two pixels to one, which has 32, keeps its full drawing. In both sheets every line's width is its drawn width times `--icon-line`, which the icon sets from its size (`lineScale`): 4/5 of drawn where there is room (`SPRITE_STROKE`), and heavier as it shrinks so an outline never comes out under 1.4 screen pixels, with no step from one size to the next; the wide strokes laid under a colored line are never made heavier. A small drawing's lines follow the same curve through `--icon-small-line`, 1 being as drawn, for 16 pixels on a plain screen. Its size is rounded to whole pixels of the screen (CSS `round()`), so it is not blurred. An icon may have a second, simpler drawing in `src/ui/icons/small/` under the same name, with 3-wide lines and nothing finer than 2 units: the small sheet and the atlas draw it from that, as a speech bubble is 8 to 30 pixels across in the scene and an icon beside words 15 to 20. Every speech bubble and marker has one, as do the roles and rooms whose picture a simpler drawing keeps, and the interface icons measured at 20 pixels and under in the menus and inspectors. A room's sign in the scene is drawn from its one drawing all the same. An icon without one is made small from its one drawing: lines at 2.9 (`SMALL_STROKE`), cream and sand fills turned white so they stand off the cream interface, and an award without its medal. Only the `bubble`, `marker`, `room` and `role` families go into the atlas, each both on its own (as a sticker with a white edge) and in a white speech bubble; the alarms (`ALARMS` in `scripts/icons.mjs`) also in a red bubble, their red turned navy and a white "!" badge at the top right, the needs (`NEEDS`) in an amber one, and the roles and the staff marker on a disc in the purple of the squares staff use furniture from, without a role's own orange disc. Cells are 128 pixels with 16 of gutter between them, and the atlas is drawn on a canvas in the headless browser and each clear texel given the color of the ink nearest it (`bleed`) before it is saved, so as the graphics card shrinks it no edge darkens. Speech bubbles draw in the bubble form, white for whatever the sim says and red or amber only when `bubbleWanted` sees trouble at that moment, and the sim says them by id (`say(c, 'bubble-happy')`, typed `BubbleId`); room signs, the markers over broken or filthy items and a guest's over the squares an item is used from draw plain; every scene icon's texture is a corner of the one atlas, so the graphics card holds one picture however many icons show. The game loads the atlas before it draws (`loadIcons()`). `/icons.html` on the dev server shows the whole set at the sizes the interface uses and over clay people from the game's camera. The interface draws no emoji: every `icon` in the data tables is an `IconId`, sentences are words alone, and a component puts the icon beside them with `<IconText id>` (an icon as tall as the words) or `<Line>` for the notes in `ui/lib/` that return `{ icon, text }`. A toast takes an icon as its last argument. An icon on a navy surface (the tooltip, the title screen's panel) sits on a cream chip, so its navy outline still shows.

## Interface (`src/ui/`)

- `hud.ts` holds the interface's own state: which menu and dialog are open, and the toasts and announcements on screen. The rest of the app talks to it.
- `components/` has one component per panel, menu, inspector and dialog, each with its styles in it, written with Panda CSS (see Styling below). Components read the game through `hooks/` and redraw when `hud.ts` says to.
- `lib/` holds the decisions as pure functions: what the menus offer, status text, chart sizing.
- `theme/panda/` holds the palette and the styles everything shares, which `panda.config.ts` hands to Panda.

Buttons act on press, not release, through the shared `Button` component.

### Styling

The interface is styled with [Panda CSS](https://panda-css.com), compiled away at build time: a component's styles are `css({...})` objects in its own file, written with the theme's tokens, and come out as plain class names and CSS, with nothing of Panda left to run in the game. The theme is in `theme/panda/`: the palette and the roles that name what each color is for, the scales of spacing, sizes, radii and type, named lines, shadows, opacity, motion and layers, and the recipes for the looks many components share. A lint rule keeps components on it. All of it, with how to add to the theme and how the cascade works, is in [dev/styling.md](styling.md).

## Desktop app (`electron/`)

`main.ts` opens one window and locks it down: sandboxed, no navigation away from the game, no new windows, every permission refused. Only one copy of the app runs at a time, since two would save over each other. `preload.ts` hands the page the small API declared in `api.ts`, and `src/app/desktop.ts` is where the game reads it. In a browser that API is absent and the game hides what depends on it. `backup.ts` keeps a copy of every save in files, in a folder for each profile, `prefs.ts` the window's own settings (full screen or not), and `updates.ts` runs the updater ([dev/releasing.md](releasing.md#updates)). `reports.ts` sends the app's crashes and hangs to Sentry along with the page's own, and `heartbeat.ts` keeps a note while the app runs, so a run that never quit cleanly is reported at the next launch ([dev/releasing.md](releasing.md)).

The built game is loaded as a file on purpose. Saved games are kept per address, so serving it any other way would hide every save a player already has.

## Saved games (`src/storage/`)

The autosave and up to twenty named saves live in the browser's storage, with export and import to move a game between the browser and the app. The desktop app also keeps a copy of each in files (`electron/backup.ts`) and puts them back if the page's storage loses them. `SAVE_VERSION` in `core/state/game.ts` marks the format, and `core/state/upgrade.ts` fills in whatever an older save lacks. When a field is added to `GameState`, give it a default there. Opening a game moves the autosave of the one being left to "Previous game", and the game already there is first kept as a save of its own if it is the last of its center (`keepLastInCenter` in `storage/saves.ts`), so moving between centers never drops one; the campaign's Continue picks up a center's latest save.

Everything kept is either a profile's or the computer's (`storage/profiles.ts`). A profile, one for each person sharing the computer, keeps its saves, autosave and "Previous game" and their pictures, its campaign, templates, welcome and tutorial, controls, choices for new games and Stats charts: each module reads and writes its key through `profileKey`, which gives the first profile the keys from before there were profiles, so nothing was moved for it, and every other profile the same keys after `profile:<id>:`. The display, the sound, dev mode (`pressure-point-dev`, apart from the profile's controls) and whether statistics are shared are the computer's. With nothing stored about profiles there is one, the first, "Player 1". A page reads which profile it plays once, preferring this tab's (in session storage) to the one played last, so a game never starts saving to another profile because another tab switched; switching, on the title screen only, reloads the page. A tab whose profile is deleted in another stops saving and says so (`profileGone`), and whatever is left under a profile the list no longer has is swept as a page opens (`sweepProfiles`), but only by a list that reads whole. A list that will not read is never taken for the first profile alone: the profiles are worked out again from the keys in storage (`rebuildProfiles`), or put back from the desktop app's copy; a list put back, or one that reads only in part, gains a profile for every one still keeping anything (`withKept`), so a copy that missed a change loses no profile. A key added to a profile goes in `PROFILE_KEYS` or `PROFILE_PREFIXES` too, so deleting the first profile takes it with the rest, which `profiles.test.ts` checks. Each profile has its own PostHog id, the first keeping the one it had ([dev/analytics.md](analytics.md)). In the desktop app the first profile's copies stay in `saved-games`, every other's go in `profiles/<id>`, and the list of profiles in `profiles.json`: a page whose storage has lost the list gets it back with every profile's saves, and is loaded again for the profile played last (`startBackup`). The first profile's copies are dropped only when it is named, as `first`.

| `yarn test`         | Unit tests: the simulation, the grid, saves, and the pure functions everywhere.                                      |
| `yarn test:e2e`     | The real game in a headless browser, driven by mouse and keyboard.                                                   |
| `yarn test:desktop` | The built desktop app: sandbox, preload API, quitting, exporting a save.                                             |

| `yarn test:perf`    | Draw calls, GPU memory over a long session and idle work, in the real game in a browser.                             |
| `yarn bench`        | The simulation's time per frame as the crowd grows. Reported, not checked.                                           |

## Conventions

- **Strict TypeScript, ESLint and Prettier.** `yarn typecheck`, `yarn lint` and `yarn format:check` must pass; CI runs them.
- **Every function has a one-line JSDoc comment** saying what it does. No tags and no type annotations: the types say the rest. The linter requires it.
- **Small pure functions, exported and tested.** Keep classes and components thin and put the working out in functions that can be tested alone. `src/app/tools/`, `src/ui/lib/` and `src/core/sim/` are the models to follow.
- **Classes are for long-lived objects that own state**, such as the view, a render layer, the audio engine or the tool in hand. Everything else is functions.
- **File names:** component files are PascalCase (`Objectives.tsx`). Every other file is lowercase or kebab-case.
- **Type-only imports use `import type`**, so they load nothing at run time. The linter requires it.
- **Every bug fix comes with a test** that fails on the old code and passes on the fix.
- **American English** in code, comments, interface text and docs.
- **Conventional Commits** for commit messages (`feat: ...`, `fix: ...`, `refactor: ...`), in lowercase. commitlint checks each message as it is committed (a Husky hook, set up by `yarn install`) and again in CI.

## Common changes

**Add an item.** Add its type to `ItemType` and an entry to `ITEMS` in `core/data/`, then a model in `render/models/items/` and a line in that folder's `index.ts`. The compiler will not build until every item type has a model.

**Add a center.** Add its id to `CenterId` and an entry to `CENTERS`: a plot that passes `plotFits`, starting money and three stars of goals. A new kind of objective is a case in `GoalSpec` and in `objectiveFor`.

**Add a discipline.** Add an entry to `DISCIPLINES`, a room, its items, a staff role, and its modalities and conditions, all in `core/data/`, then a model for each new item. The simulation, the menus and Settings pick it up from the data.

**Change the icon or the logo.** Edit `brand/icon.mjs` or `brand/wordmark.mjs` and run `yarn brand`, which renders the app icon (`build/icon.png`, picked up by the installers), the favicon (`public/favicon.svg`) and the logo on the title screen (`src/ui/theme/logo.png`). Commit what it writes. The banner at the top of the README (`docs/assets/hero.jpg`) is a picture with the logo in it, so it needs redrawing too.

**Add an icon.** Draw it in `src/ui/icons/`, as `family-name.svg` on `viewBox="0 0 32 32"`: rounded shapes with a navy outline (`stroke="#24384a"`, 2.25 wide, round caps and joins, and no navy line under 1.6 after any scaling; the interface draws lines as wide as the size calls for, 4/5 of drawn at 24 pixels and over, while the scene's atlas keeps them as drawn) and one fill for its family (rooms teal plates, roles orange discs, people orange, faces and hands an emoji's yellow, warnings red, money gold, things cream and sand), from the palette in `ui/theme/panda/palette.ts`. No text, ids, styles, gradients or references: every icon shares one page. Its ink should be 23 to 30 units across, clear of every edge by half a unit. Keep it simple enough to read at 24 pixels. If it is a speech bubble or a marker, or it will sit beside words and does not survive being made small by the build, draw it again in `src/ui/icons/small/` under the same name: at most four or five shapes, every line 2.8 wide or more (3 as a rule), no dot or arc under 2 units, white rather than cream or sand, nothing inside a disc. Run `yarn icons`, which refuses a drawing that breaks those rules (a speech bubble's or marker's large drawing is spared the lints of line and ink, as its small drawing keeps the stricter ones, and a drawing picked as it is can be spared one in `SPARED`), then check it on `/icons.html` beside the rest, at 12 and 16 pixels too, and commit the drawing with what `yarn icons` wrote. A unit test fails if the built files are out of date with the drawings. Use it as `<Icon id="family-name" />` or `iconTexture('family-name')`; a scene icon outside the four families the atlas holds needs its family added to `SCENE_FAMILIES` in `scripts/icons.mjs`.

**Add something the desktop app can do.** Declare it in `electron/api.ts`, implement it in `preload.ts` and `main.ts`, and read it through `src/app/desktop.ts`. Check that the web build still works without it.
